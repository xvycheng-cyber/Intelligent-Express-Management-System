| 项目 | 内容 |
| --- | --- |
| 文档版本 | v1.0 |
| 解析器 | `AddressParserService`（规则解析，无状态、纯逻辑） |
| 关联文档 | `requirements.md`（BR-01～BR-08、BR-13、BR-15）、`api-design.md`（§3.1 响应结构）、`test-plan.md`（TC-PARSE 用例） |
| 设计原则 | **规则优先**；先规则、后 AI（AI 属 P2，MVP 不实现）；解析与保存彻底分离；解析结果必须可人工核对与修改 |

---

## 1. 目标与非目标

### 1.1 目标

1. 把多行文本按"一行一条联系人"解析为 `{姓名, 电话, 详细地址}`。
2. 兼容中文/英文分隔符、Tab、Excel 粘贴、字段顺序不同、字段缺失。
3. 地址"原样保留"：只去掉字段边界处的分隔符，不切分、不改写内部标点。
4. 每行都返回原始行号、原始文本、状态与**具体失败原因**，失败不影响其它行。
5. 解析过程零副作用：不写库、不发网络请求、不写文件、无随机、可重复。

### 1.2 非目标

- 不做地址标准化/纠错/补全省市区（需要行政区划库）。
- 不做姓名性别推断、电话归属地查询。
- 不做 OCR、语音、图片输入。
- MVP 不调用任何大模型接口。

## 2. 规则总表

| 编号 | 规则名称 | 一句话说明 |
| --- | --- | --- |
| PR-01 | 输入预处理 | 去 BOM、统一换行、长度限制；保留原始文本 |
| PR-02 | 行切分与空行 | 按 `\r\n`/`\n`/`\r` 切行；空行跳过并计数 |
| PR-03 | 电话识别与规范化 | 用模式定位电话（手机/座机/脱敏），并做展示级规范化 |
| PR-04 | 姓名识别 | 姓名型片段判定 + 位置候选（电话前/电话后/电话前最后一段） |
| PR-05 | 地址提取 | 从**原字符串**中剔除姓名段与电话段，其余原样保留 |
| PR-06 | 分隔符集合 | 中英文逗号、中英文分号、Tab；顿号与空格**不作**分隔符 |
| PR-07 | 字段顺序无关 | 支持"姓名,电话,地址""电话,姓名,地址""姓名,地址,电话""地址,姓名,电话" |
| PR-08 | 长度与边界校验 | 姓名 ≤50、电话 ≤20、地址 ≤255；与数据库列宽一致 |
| PR-09 | 行状态与错误聚合 | 一行可同时返回多个错误；`VALID` 需三字段齐全且合法 |
| PR-10 | 纯函数 | 不依赖 Spring 容器、不注入 Mapper、无 IO |
| PR-11 | 字符规范化范围 | 仅对**匹配用副本**做全角→半角与大小写处理，不改变保存值 |
| PR-12 | 输出稳定性 | 相同输入必然得到相同输出；行序与输入一致 |
| PR-13 | 批量上限 | 有效行 ≤200、单行 ≤500 字符、原文 ≤20000 字符；上限由 Controller/Service 在调用解析器**之前**校验，解析器本身只处理传入文本（不抛 HTTP 业务码） |

## 3. 字符与分隔符处理

### 3.1 分隔符（PR-06）

| 分隔符 | 码点 | 是否作字段分隔 | 说明 |
| --- | --- | --- | --- |
| 中文逗号 `，` | U+FF0C | ✅ | 任务书示例主分隔符 |
| 英文逗号 `,` | U+002C | ✅ | Excel/英文输入法常见 |
| 制表符 `\t` | U+0009 | ✅ | 从 Excel 复制粘贴 |
| 中文分号 `；` | U+FF1B | ✅ | 用户习惯 |
| 英文分号 `;` | U+003B | ✅ | 同上 |
| 顿号 `、` | U+3001 | ❌ | 地址中可能合法出现（"XX路、XX街"），不切 |
| 普通空格 | U+0020 | ❌ | 英文姓名、地址中可能合法出现 |
| 全角空格 | U+3000 | ❌（仅 trim） | 只用于去首尾空白 |
| 竖线（U+007C）、斜杠 `/` | — | ❌ | 避免误伤地址中的 `12/301` |

> 设计取舍：分隔符越少越安全。用"电话模式 + 姓名模式"定位字段，比"多切几刀"更稳。

### 3.2 空白字符集合

`Character.isWhitespace(c) || Character.isSpaceChar(c)`，覆盖：普通空格、Tab、全角空格 U+3000、不换行空格 U+00A0。解析时用于 trim，**不用于切分字段**。

### 3.3 匹配用规范化（PR-11）

只作用于"匹配副本"，且必须**等长替换**（保证能在原串中换算索引）：

| 处理 | 范围 | 是否影响保存值 |
| --- | --- | --- |
| 全角数字 `０-９` → 半角 | 匹配副本 | 否 |
| 全角字母 `Ａ-Ｚａ-ｚ` → 半角 | 匹配副本 | 否 |
| 全角 `＋` `－` `＊` → 半角 | 匹配副本 | 否 |
| 去除包裹括号 `()（）[]【】`（仅电话候选两侧） | 匹配副本 + 剔除范围 | 是（包裹符随电话剔除） |
| 大小写：`X` 与 `x` 等价 | 匹配时忽略 | 否（保存原字符） |

> 保存的 `phone` 是"去掉首尾空白与包装括号后的原值"，不是匹配副本。`１３８００１３８０００` 这类全角输入解析后仍保存为全角原值还是半角？—— **统一转半角后保存**，因为全角数字无法用于拨号/校验，属于明确的格式错误。此条作为 PR-03 的一部分单独说明。

## 4. 算法流程

```text
parse(rawText)
 ├─ PR-01 预处理：去 BOM、CRLF/CR → LF（保留原始行文本用于回显）
 ├─ PR-02 按 \n 切分 → lines[]
 │    空行（trim 后为空）→ skippedLines++，继续
 │    单行长度 > 500 → 该行 INVALID(E110)
 ├─ 逐行 parseLine(line, lineNo)
 │    ├─ 1) 生成等长匹配副本（全角→半角）
 │    ├─ 2) 定位电话候选（PR-03）
 │    │      a. 先找"整段即电话"的分隔段
 │    │      b. 再在整行找手机/脱敏/座机模式
 │    │      c. 找不到 → E103，phone=null
 │    ├─ 3) 以电话位置把原行切成 before / after
 │    ├─ 4) 姓名候选（PR-04）：
 │    │      4.1 before 首段是姓名型 → 姓名=该段
 │    │      4.2 before 末段是姓名型（且首段不是）→ 姓名=该段
 │    │      4.3 before 为空/无姓名型 → 在 after 首段找姓名
 │    │      4.4 有类姓名候选但违规 → E106；完全无候选 → E102
 │    ├─ 5) 地址 = 原行剔除姓名段与电话段后的剩余原文（PR-05）
 │    │      剩余 trim（去首尾分隔符/空白）
 │    │      为空 → E105
 │    ├─ 6) 校验（PR-08）：姓名长度/字符、电话格式、地址长度
 │    └─ 7) 聚合错误（PR-09）→ status
 └─ 汇总 counts → ParseResult
```

### 4.1 为什么要"从原串剔除"而不是"重新拼接"

- 如果按分隔符切分再 `join("，")`，会改变用户原文的标点（原本英文逗号的地址被改成中文逗号），违反 BR-04。
- 从原串剔除两段后留下的子串，天然保留了地址内部的所有逗号、顿号、括号、空格。
- 实现上用 `StringBuilder` 按区间拼接剩余片段即可，索引由步骤 2 的匹配位置给出（匹配副本等长，索引可直接复用）。

### 4.2 电话定位（PR-03）

候选模式（在匹配副本上匹配，使用边界断言避免截断长数字）：

| 类别 | 正则（示意） | 说明 |
| --- | --- | --- |
| 手机 | `(?<!\d)(?:\+?86[-\s]?)?1[3-9]\d{9}(?!\d)` | 11 位大陆手机号，允许 `+86` 前缀与中间空格/短横 |
| 脱敏手机 | `(?<!\d)1[3-9]\d{2}[xX*]{4}\d{4}(?!\d)` | 任务书示例 `136xxxx0000`，见 BR-13 |
| 座机 | `(?<!\d)(?:\+?86[-\s]?)?0\d{2,3}[-\s]?\d{7,8}(?:-\d{1,6})?(?!\d)` | 含区号，允许短横 |

选择策略（确定性，按优先级）：

1. **整段优先**：若某个分隔段在去除首尾空白、包裹括号、内部空格与短横后完全匹配上述任一模式 → 直接选它。
2. 否则按"手机 → 脱敏手机 → 座机"的顺序，取**最先出现**的匹配。
3. 同一行出现多个不同号码 → 取优先级最高、位置最靠前者为电话，其余号码**留在地址原文中**（不报错，因为地址里可能含门牌/电话分机）。
4. 候选为空 → `E103`（未识别到联系电话）。
5. **纯数字段兜底判定（决定 E103 还是 E104/E108）**：若某个分隔段在去除首尾空白后是"仅由数字/短横/空格组成的 5～30 位串"（如 `12345`、`1380013800`），视为**电话候选存在但不合法**：长度 >20 → `E108`，否则 → `E104`；完全找不到此类段 → `E103`。
6. 候选存在但规范化后仍不匹配任何模式（例如 10 位手机号、以 2 开头的 11 位数字）→ `E104`（电话格式不正确）。

规范化（作用于解析输出值；保存服务在落库前复用同一规则，保证库中格式统一）：

1. 去首尾空白与包裹括号 `()（）[]【】`。
2. 去掉 `+86` / `86` 前缀（仅当后接 1[3-9] 手机号）。
3. 去掉内部空格与短横（座机同样处理，如 `0571-88888888` → `057188888888`）。理由：电话是标识符，统一格式便于查找与去重；展示层不要求保留分隔。
4. 全角数字/字母转半角。
5. 结果长度 ≤20。

> 关于"脱敏手机号"：这是**有意接受**的形态（任务书示例即如此），用于课程演示与截图脱敏；规则、测试用例、论文中都明确写出，不做隐性妥协。若后续要求严格企业级校验，只需关闭该分支并追加一条用例（见 `test-plan.md` TC-PARSE-011）。

### 4.3 姓名识别（PR-04）

姓名型片段判定（对候选段 trim 后）：

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 中文姓名 | `^[\u4e00-\u9fa5·]{2,15}$` | 菜小鸟、欧阳·娜娜 |
| 英文姓名 | `^[A-Za-z][A-Za-z .'\-]{1,29}$` 且至少含 1 个字母 | John Smith、Mary-Jane |
| 允许包裹 | 成对引号/括号可去除后判定 | `"菜小鸟"`、`[菜小鸟]` |
| 排除 | 含任何数字 | `菜小鸟12` |
| 排除 | 含地址关键词 | 省/市/区/县/镇/乡/村/街/路/巷/弄/号/栋/幢/座/单元/楼/层/室/苑/园/小区/大厦/广场/公寓/社区 |
| 排除 | 含 `@`、`://`、`http` | 邮箱、网址 |
| 排除 | 长度 > 50 | 明显不是姓名 |

候选顺序（确定性）：

1. `before`（电话之前的部分）按分隔符切出的**第一段**；无分隔符时 `before` 整段即第一段；
2. 若第一段不是姓名型，取 `before` 的**最后一段**（兼容"地址,姓名,电话"）；
3. 若 `before` 无姓名型，取 `after`（电话之后）的**第一段**（兼容"电话,姓名,地址"）；
4. 全部失败时区分两种错误：
   - 存在"像姓名的候选段"（不含地址关键词、不含电话、长度 ≤50，但含数字或特殊字符）→ `E106`（姓名不合法）；
   - 完全找不到候选段（例如首段就是"浙江省杭州市…"）→ `E102`（未识别到姓名）。

若姓名型片段同时像地址（含地址关键词）则不算姓名 —— 由排除规则保证。

### 4.4 地址提取（PR-05）

1. 在原始行上标记待剔除区间：姓名区间（若识别到）与电话区间（若识别到）；两者都缺失时整行即候选地址。
2. 剩余区间按原顺序拼接，得到候选地址。
3. `trim` 掉首尾的：空白字符 + 分隔符（`，,;；\t`），**循环执行**直到两端都不是空白/分隔符（英文地址会连续出现 `, ,`）。
4. 结果为空 → `E105`。
5. 长度 > 255 → `E107`。
6. 不做任何字符替换、不合并连续空格、不删除内部标点。

示例：`菜小鸟，浙江省杭州市,西湖区、XX路12号，13800138000`
→ 剔除"菜小鸟"与电话段后，剩余含 `，浙江省杭州市,西湖区、XX路12号，` → trim 首尾分隔符 → `浙江省杭州市,西湖区、XX路12号`（英文逗号与顿号原样保留）。

### 4.5 行状态（PR-09）

- `VALID`：姓名、电话、地址三者都存在且全部通过 PR-08 校验，`errors` 为空。
- `INVALID`：任一校验失败；`errors` 可含多条。
- 部分解析成功时**保留已识别的字段**（例如姓名识别成功但电话缺失），让用户在预览表里只补缺失项，而不是面对整行空白。

## 5. 行级错误码（E1xx）

| 错误码 | field | message（面向用户） | 触发条件 |
| --- | --- | --- | --- |
| E102 | `receiverName` | 未识别到收件人姓名，请按"姓名，电话，地址"顺序填写 | 无任何姓名型片段（如首段就是地址） |
| E103 | `phone` | 未识别到联系电话 | 全行无电话候选 |
| E104 | `phone` | 联系电话格式不正确 | 有候选（含 5～30 位纯数字段）但不符合手机/座机模式 |
| E105 | `fullAddress` | 未识别到详细地址 | 剔除姓名与电话后为空 |
| E106 | `receiverName` | 收件人姓名不合法（不能含数字，长度 2～50） | 有类姓名候选，但含数字/特殊字符/超过 50 字 |
| E107 | `fullAddress` | 详细地址过长（最多 255 字） | 地址 > 255 |
| E108 | `phone` | 联系电话过长（最多 20 位） | 电话 > 20 |
| E109 | `fullAddress` | 该行字段过多，无法确定地址边界 | 分隔段 > 6 且地址候选为空 |
| E110 | `rawLine` | 单行内容过长（最多 500 字符） | 单行 > 500 |
| E111 | `receiverName` | 收件人姓名过长（最多 50 字） | 姓名 > 50 |

> `E101` 保留不用（历史编号占位），避免与"空行跳过"混淆；空行不计错误，只计入 `skippedLines`。

**错误对象结构**：

```json
{ "code": "E103", "field": "phone", "message": "未识别到联系电话" }
```

## 7. 伪代码（实现契约）

```java
public ParseResult parse(String rawText) {
    // PR-01: 去 BOM，统一换行；保留原始行
    String text = normalizeNewlines(stripBom(rawText));
    String[] rawLines = text.split("\n", -1);

    int totalLines = rawLines.length, skipped = 0;
    List<ParsedItem> items = new ArrayList<>();

    for (int i = 0; i < rawLines.length; i++) {
        String rawLine = rawLines[i];
        if (isBlank(rawLine)) { skipped++; continue; }          // PR-02
        int lineNo = i + 1;                                     // 1-based，保留空行位移
        if (rawLine.length() > 500) {                           // PR-13
            items.add(invalid(lineNo, rawLine, error("E110", "rawLine", "单行内容过长（最多 500 字符）")));
            continue;
        }
        items.add(parseLine(rawLine, lineNo));
    }
    return buildResult(totalLines, skipped, items);
}

private ParsedItem parseLine(String rawLine, int lineNo) {
    String matchCopy = toHalfWidth(rawLine);                    // PR-11，等长
    PhoneMatch phone = phoneExtractor.locate(matchCopy, rawLine); // PR-03，返回原文索引
    List<LineError> errors = new ArrayList<>();

    if (phone == null) errors.add(error("E103", "phone", "未识别到联系电话"));

    NameMatch name = nameExtractor.locate(rawLine, matchCopy, phone); // PR-04
    if (name == null) errors.add(error("E102", "receiverName", "未识别到收件人姓名"));

    String address = phone == null && name == null
            ? null
            : addressExtractor.remain(rawLine, name, phone);       // PR-05，原文剩余

    validate(address, name, phone, errors);                     // PR-08/09
    return new ParsedItem(lineNo, rawLine, errors.isEmpty(), name, phone, address, errors);
}
```

| 类 | 职责 | 依赖 |

| `AddressParserService` | 唯一对外入口，编排流程；`@Service` 但**不注入任何 Mapper** | 仅 JDK + 同包工具 |
| `PhoneExtractor` | PR-03 | `PhonePatterns` |
| `NameExtractor` | PR-04 | `NamePatterns`、`AddressKeywordFilter` |
| `AddressExtractor` | PR-05 | — |
| `LineSplitter` | PR-01/02 | — |

## 8. 复杂度与限流

| 项 | 值 |
| --- | --- |
| 单行时间复杂度 | O(L)，L 为行长；正则为线性回溯（无嵌套量词） |
| 整批复杂度 | O(总字符数) |
| 有效行上限 | 200（由 Service 在调用前校验，超出返回 40003） |
| 单行上限 | 500 字符（超出该行 E110，由解析器标记） |
| 原文上限 | 20000 字符（由 Service 在调用前校验，超出返回 40003） |
| 大文本策略 | 先按行切分并计数，超限直接拒绝，不做部分解析 |

## 9. 与"保存"的边界

| 动作 | 解析器 | 保存服务 |
| --- | --- | --- |
| 读数据库 | ❌ 禁止 | ✅ |
| 写数据库 | ❌ 禁止 | ✅ |
| 校验格式 | ✅（行级，宽松，给出原因） | ✅（字段级，严格，任一失败整批拒绝） |
| 修改用户输入 | ❌ 不改 `rawLine`；输出字段是对原串的切片（地址去边界分隔符、电话规范化） | 电话按 PR-03 规范化；姓名/地址只 trim |
| 决定是否入库 | ❌ 不参与 | ✅ 唯一入口 |

一次典型请求的调用链：

```text
[识别]  POST /api/addresses/parse → AddressController.parse → AddressParserService.parse → 返回 items（内存）
[确认]  前端表格编辑 → POST /api/addresses/batch → AddressController.batchSave → AddressService.batchSave
        → 逐条 Bean Validation → AddressMapper.insert → 事务提交
```

两次请求之间**没有任何持久化状态**；即使用户关掉页面，也不会留下"解析草稿"。

## 10. 规则优先，AI 后置（P2）

```java
public interface AddressParseStrategy {
    String name();
    ParseResult parse(String rawText);
}
```

| 阶段 | 策略 | 默认 |
| --- | --- | --- |
| MVP | `RuleBasedParseStrategy`（即本文件的规则） | ✅ 启用 |
| P2 | `AiAssistedParseStrategy` | ❌ 关闭（`app.parser.ai.enabled=false`） |

AI 策略的硬性前置条件（写进架构约束，未满足不得开启）：

1. 只对**规则解析失败**的行做二次尝试，且由用户显式点击"AI 辅助识别"。
2. 发送前必须脱敏：姓名保留姓、电话中间四位打码、地址截断到区县。
3. 超时 ≤3 秒，失败自动回退规则结果。
4. 上传内容与响应不得写入日志。
5. 云端处理需在界面给出明确告知与开关，默认关闭。
6. 不因 AI 策略而改变 `/api/addresses/parse` 的响应结构。
